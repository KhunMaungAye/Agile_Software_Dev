## 2. Project Context

Students and staff may lose personal belongings such as mobile phones, wallets, student ID cards, keys, books, bags, and other items around campus.

Currently, lost and found information may be communicated through social media, messaging applications, group chats, or word of mouth. These methods can make it difficult to search for previous reports, update information, and determine whether an item has already been returned.

The Smart Campus Lost & Found Website will provide a centralized online platform where campus users can report lost items, report found items, search for reports, and update the status of items.

## 3. Problem Definition

The current process for managing lost and found items is not centralized. Students may have difficulty finding relevant reports because information is distributed across different communication channels.

The project aims to solve this problem by providing one website where lost and found information can be organized, searched, and managed more easily.

## 4. Product Vision

To create a simple and accessible digital platform that helps students and staff quickly report, search for, and recover lost belongings on campus.

## 5. Project Goals

The MVP will allow users to:

1. Submit a report for a lost item.
2. Submit a report for a found item.
3. Browse available lost and found reports.
4. Search for items using keywords.
5. Filter reports by category, location, and status.
6. View detailed information about an item.
7. Submit a basic claim or contact request.
8. Mark an item as resolved after it has been returned.

## 6. Key Objectives

The project team will:

- Develop a simple and responsive Lost & Found website.
- Make reporting a lost or found item quick and understandable.
- Provide effective search and filtering functions.
- Organize item information using categories and locations.
- Provide clear item status information.
- Reduce duplicated or outdated reports.
- Protect unnecessary personal information.
- Apply Agile development practices throughout the project.
- Test each completed feature against defined acceptance criteria.

## 7. MVP Scope

### Included Features

The first version of the system will include:

- Homepage and navigation.
- Lost Item Report form.
- Found Item Report form.
- Lost & Found item listing.
- Keyword search.
- Category filtering.
- Location filtering.
- Status filtering.
- Item details page.
- Lost, Found, and Resolved statuses.
- Basic claim/contact request.
- Input validation.
- Error and success messages.
- Responsive desktop and mobile interface.
- Database storage for item reports.

### Excluded Features

The following features are outside the MVP:

- Mobile application.
- GPS tracking.
- CCTV integration.
- AI image recognition.
- Facial recognition.
- Payment functionality.
- Delivery services.
- Government or police database integration.
- Advanced identity verification.
- Push notifications.
- Multi-university support.

These features may be considered as future improvements through the product backlog.

## 10. Project Assumptions

The project assumes that:

- Users have access to the internet.
- Users have a modern web browser.
- Users can provide basic information about lost or found items.
- Users can identify approximately where and when an item was lost or found.
- Users will provide reasonably accurate information.
- The initial system will focus on the Siam University campus.
- Users understand that reporting an item does not guarantee its recovery.

## 11. Project Constraints

The project is constrained by:

- Limited development time during the university course.
- Limited student development resources.
- Limited testing resources.
- Dependence on internet and database availability.
- Possible inaccurate information submitted by users.
- Privacy requirements for user-submitted information.
- The need to keep the MVP small enough to complete within the course schedule.

## 12. Risk Management

| **Risk**                   | **Possible Impact**                             | **Response**                                         |
| -------------------------- | ----------------------------------------------- | ---------------------------------------------------- |
| Incorrect item information | Users may search for the wrong item             | Use required fields and clear reporting instructions |
| Fake claims                | An item could be claimed by the wrong person    | Introduce basic verification questions               |
| Duplicate reports          | Search results may become confusing             | Encourage users to check existing reports            |
| Old reports remain active  | Users may waste time contacting old reports     | Provide a Resolved status                            |
| Privacy problems           | Personal information could be exposed           | Collect and display only necessary information       |
| Database failure           | Item reports may become temporarily unavailable | Add error handling and backup procedures             |
| Scope expansion            | MVP may not be completed on time                | Prioritize Must-have backlog items                   |
| Low user adoption          | Users may continue using social media           | Keep the system simple and easy to use               |

## 13. Agile Development Strategy

The project will use an Agile/Scrum approach.

Development will be divided into short iterations called **sprints**. At the beginning of each sprint, the team will select high-priority user stories from the product backlog.

During development, the team will:

- Plan sprint work.
- Develop selected features.
- Test completed features.
- Review the increment.
- Collect feedback.
- Conduct a retrospective.
- Update and reprioritize the backlog.

A user story will only be accepted when its acceptance criteria have been successfully tested.

## 15. Success Criteria

The project will be considered successful when:

- All Must-have requirements are implemented.
- Users can successfully report lost items.
- Users can successfully report found items.
- Users can search and filter reports.
- Users can view item details.
- Users can identify an item's current status.
- Users can submit a basic claim/contact request.
- The website works on both desktop and mobile screen sizes.
- At least 80% of test users can complete the main tasks without assistance.
- No critical defects remain before final submission.

## 16. Definition of Done

A user story is considered **Done** when:

- All acceptance criteria pass.
- The feature has been implemented and integrated.
- Functional testing has been completed.
- Relevant errors have been fixed.
- The feature works on supported desktop and mobile screen sizes.
- Basic accessibility has been checked.
- Another team member has reviewed the implementation where possible.
- No passwords, API keys, or other secrets are stored in the repository.
- Related documentation has been updated.

## 17. Project Approval

This Project Charter establishes the initial direction and scope for the **Smart Campus Lost & Found Website**.

The Product Owner will prioritize the product backlog and approve completed user stories. Any major change to the MVP scope should be discussed and reviewed before development to ensure that the project remains achievable within the course schedule.

The project team is authorized to develop, test, and demonstrate the MVP according to the objectives, requirements, and Agile practices described in this charter.
